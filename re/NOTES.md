# PLASTIK (Purple, The Party 1998) - reverse-engineering notes (running log)

Status after session 1: container/DLL formats identified, original boots under Unicorn and runs the whole demo with a virtual clock, golden frames captured (video + per-frame CRC), web player = captured video + libopenmpt. **No effect is ported yet.** Next step = pick one scene (A: credits/logo, simplest) and port it, diff against `RAW=` frames.

## Unpack / entry
`re/unpack_clean.py OUT.bin` runs the EXE's own loader under Unicorn (via `unpack_pmodew.py`, copied from pls_amb: real-mode first stage, switch to PM, DOS file I/O on the EXE) until the Watcom `_cstart` and dumps 64 MB RAM (~1.5 s). Args: `PLASTIK.EXE 0x2cb0 0x3ce` (image end = PMW1 offset, SS from the MZ header), **entry 0x5386c** (the `jmp` before the string "WATCOM C/C++32 Run-Time system"), GDT at 0x1be80, stack ESP 0x124f1e0 (kept from the dump). Flat model like pls_amb: CS=0x868, DS=0x860 base 0.
Memory map: code 0x10000-0x60000 (demo effects 0x1d000-0x2b000, MIDAS 0.6.1 0x2c000-0x3d000 with its `midasdll` wrappers 0x3d1xx, Watcom RTL 0x50000+), data/bss 0x100000-0x124f000 (strings at 0x101000, tables built at start up to 0xec0000..).

## Harness (re/emucore.py, re/harness.py)
`emucore.py` = pls_amb's emulator core with: PL_MEM env (image), GDT 0x1be80, INT 21h AH=06 (console), **VBE**: 4F00 (info block must keep the mode list inside the first 256 B: the program allocates only 0x200 B of DOS memory and the next block overlaps; modes 0x100 640x400x8, 0x101, 0x111 640x480x16 565, 0x1a0 (invented number) 640x400x16 565, 64 MB video memory => "triplebuffer enabled"), 4F01, 4F02 (mode 0x1a0 | 0xc000 = LFB), **4F07 = display start (y = 0/400/800: triple buffer; each call = one finished frame, hook `on_ds`)**, DPMI 0800 maps the LFB at 0x30000000.
Python gotcha found on the way: `bytearray[a:b] = 7 bytes` into an 8-byte slice shrinks the array (the first run read the mode list one byte off).
MIDAS: no menu appears, the autodetect falls through to "No Sound" by itself (port reads return 0). Startup: 3-4 s host (loading 36 files, "Doing hierarchy", "Calculating lighttables" = the 3DS scene prep), then the first frame.

### Time model (the important part)
- The demo is a **fixed-step loop on the tick counter [0xec0030]**: each scene is `while (ticks > 1) { logic_step(); ticks--; } render(); flip();` (e.g. scene A loop at 0x28900: `cmp [0xec0030],1 / jbe` ... `dec [0xec0030]` at 0x28c4d). The counter is incremented by the MIDAS timer callback `0x3d190` (`inc [0xec0030]`), installed through `0x32f70` (= MIDAS `tmrSyncScreen`: rate = the measured display refresh, `[0xec000c]`, via `GetDisplayRefreshRate` 0x32c8c). On the target (640x400 VGA mode) this is 70 Hz.
- The music position is polled by `0x3d220` (-> `0x3d1d4` = MIDASgetPlayStatus copy: struct [0]=order -> [0xec0024], [4]=pattern -> [0xec0014], [8]=row -> [0xec002c], [0x14] -> [0xec0020]) and returns `order<<8 | row`. Scenes switch when the position reaches (order,row) (logic steps test it, e.g. cmp di,0x100 / 0x120 at 0x2892e: order 1 rows 0 and 0x20 trigger events). No audio is involved otherwise: animation = f(tick count, XM position).
- Harness: no timer ISR runs in our emulation, so at every flip we add K ticks (`[0xec0030] += K`, virtual time += K/70) and `0x3d1d4` is replaced by a lookup in `re/xm_times/system.json` (`xmtime.py SYSTEM.XM`), evaluated at the tick the logic step belongs to (`total - (pending-1)`). K=3 (23.3 fps) is the capture rate. Any K gives the same *logic*; only the frames that get rendered differ (state is cumulative per logic step, so frames at a fixed grid are the same for all K that divide the grid).
- Open: the original's real frame rate (P200: several ticks per frame) is not reproducible, nor is the exact XM-position/tick phase of the real MIDAS player (no sound card: MIDAS steps its own timer). Row boundaries land within +-1 tick of the XM-theory time.

## Scene D black = Unicorn bug (solved)
`0x1d76c` builds a log table (0xc51700: `chop(46.1662*ln x)`, x = 0..511) and an exp table (0xb80120), used to build D's palette by multiplying in the log domain. It starts at x = 0, so `fyl2x` runs with ST0 = 0 (divide by zero, masked). **Unicorn 2.1.4 does not pop the x87 stack in that case**, one stray `ln2` stays under the loop's constant and every later `fmul st,st(1)` multiplies by `ln 2` instead of 46.1662: log table = 0,0,0,0,1,1,2... instead of 0,0,31,50,63..., palette all zero, scene D black. Found by tracing the ST registers over the loop (re/harness.py HOOKL). Fix in harness.py (`fixlog`): feed x = 1 instead of 0 (same stored byte, 0). Other scenes do not use these tables. Lesson: any x87 special case (zero/inf/NaN operands) in Unicorn needs checking when a scene looks wrong.
`web/js/plastik-d.mjs` ports the table builders (log, exp, palette, 32 dark palette copies) and `tools/test-d-tables.mjs` checks them byte-exact against the original's RAM (`re/golden/d-inputs.bin`, made with `DUMPD=... DUMPAT=670 K=12 harness.py 671 ...`). The Math.log/Math.exp results match the 80-bit x87 chop results for all 512 entries.

## 3D engine facts seen so far
- Pure x87 + integer (no MMX). 3DS loader ("Calculating normals", "lighttables", "hierarchy" = node tree of the 3DS), camera names Camera01-03 chosen per scene (strings at 0x1027d8..).
- Pixel format RGB565, 640x400, triple buffer in the LFB; the final blit/clear are `rep` ops.
- Candidate asm snippet for the write-up (0x2accc..): an unrolled loop producing 4 RGB565 pixels from a 2x2 sample: per pixel `fld dword [eax*4+0xc5b740]` (4 weights) x `fmul qword [ecx*8+0xc30f00]` (ecx = table byte pair), 4 products summed, `fstp qword [0x112dd0]`, then bytes 0,2,4 of the stored double are read back and packed to 565 (`>>3`, `>>2`, `>>3` shifts). Reading channels out of the *bytes of a double* = one FPU multiply-add scales three packed channels at once. Tables at 0xc30f00 / 0xb35680 / 0xcee080 / 0xc5b740 are built at start (zero in the entry dump), so decoding the exact encoding needs a RAM dump after "Calculating lighttables". Writes each pixel twice (`[edi]` and `[edi+0x500]` = next line: 2x vertical doubling, 640x400 from 320x200 work).

## Scene D port (session 3, done)
- Method: `python3 re/x86js.py web/js/plastik-d.gen.mjs dD1.dis dD2.dis -- 1ddb4` (objdump intel listings of the D code ranges) -> one JS function per x86 function (`for(;;)switch(pc)`), flat memory + x87 stack in `web/js/x86rt.mjs`. Natives (NATIVE dict): 0x51c7a (frndint chop = Math.trunc), 0x51cad (fxch+fpatan), 0x51e3c (present), 0x3d220 (XM position), 0x29c20 (no-op), 0x2accc (hand-ported block). Dead-flag elimination keeps the output small and fast. x87 control word is 0x127f (double precision), so JS doubles are right.
- Pitfalls found by diffing RAM against the emulator: `push [esp+x]` must read the operand before decrementing esp; a PTR-less memory operand takes its size from the register operand (else 8-bit stores became 32-bit); the original reads uninitialised stack in frame 0 (replay the dumped stack at esp with esp&7==4); 0x13 is hex (`>>19`, not `>>13`).
- Display lag: the picture shown at flip k is the one rendered at flip k-1; golden frame F0 is stale (scene C leftovers). JS frame n == golden flip F0+n+1.
- Player: `DScene.step()` runs to the next present (a Stop is thrown from the present native, resume = `f_1ddb4(0x1e3c8)`); checkpoints every 50 frames store the pages that differ from the initial memory, so seeking replays at most 49 frames (~0.7 s). Calls do not write return addresses (harmless here).
- Sizes: init asset 253 KB, system-times.json 70 KB, all 15 D checkpoints 9.9 MB of RAM (in memory, built on the fly, not shipped); the web payload apart from plastik.mp4 is about 3.3 MB (XM 1.3 MB). HOOKD/HOOKL/DBGP debug hooks were removed from harness.py.
- Harness env added: `DUMPDE=x.npz STOPDE=1` (dump D's entry state, input of `re/mk_dinit.py`), `TRACE9=n`, `RAWFROM`.
- Scene D ends after 717 flips (order >= 28, ~143.4 s) when f_1ddb4 returns.

## Scenes A and B port (session 4, done: both bit-exact)
- Entry snapshots: harness `DUMPENT=hexaddr,file.npz STOPDE=1` (A = 28264, B = 26278) -> `re/mk_init.py` packs a page list (`[u32 n][u32 esp] n x ([u32 addr][4096 B])`). The page set is pruned by a PURE recompile traced with a wrapper over x86rt (every page that is READ, not just read-before-write: partial pages matter) plus the screen buffer pages (read by the present native, not by recompiled code). Sizes: A 132 pages 528 KB, B 129 pages 516 KB.
- `re/x86js.py` now disassembles on demand (objdump 0x1000-byte windows per entry/jump target; one linear listing loses sync in data islands). Only an instruction ending exactly at the window's stop address is dropped (it may be truncated; first version dropped the last new instruction of every window and made B jump into a hole at 0x27290). Run: `python3 re/x86js.py OUT.mjs code.bin -- ENTRY` (code.bin = first 0x60000 bytes of the clean RAM image).
- Instructions added: not, ror/rol imm (flags not modelled), fistp qword, pushaw/popaw, rep stos WORD (Uint16Array fill). Natives: 0x54b14 fmod, 0x536e9 (keyboard port, returns 0), 0x536f1, 0x536d1 (memset), 0x52134 (memcpy), 0x28028 (A's per-pixel alpha blend, `R.n_blend`). INLINE hand ports inside recompiled functions (checked only by the frame diff): 0x2884c (palette conversion loop) and 0x52c04 (anti-aliased line inner loop, saturating byte adds). `PURE=1` disables INLINE and the blend native.
- Speed: V8 will not TurboFan a function over ~60 KB of bytecode; B's entry function (1000 instructions) stayed in Sparkplug at ~600 ms/frame. The recompiler now splits functions over 500 instructions into chunks (`c_X_i`, registers are module-level so they are shared; `CHUNK` env). B: ~27 ms/frame, A: ~29 ms/frame average in Node (budget 43 ms), A has spikes to ~220 ms while TurboFan compiles.
- Results: A 955 frames (flips 1..955) and B 957 frames (flips 956..1912) are bit-exact against the harness RAW frames (`node tools/test-scene.mjs a|b INIT RAW_DIR n`); seek checkpoints verified (`tools/test-seek.mjs a|b|d`); `tools/uitest.mjs` shows the canvas for A, B and D. Golden flip 0 (blank) is not reproduced. sin/cos/atan2 use JS Math (no difference seen); keyboard `in al,dx` assumed 0.
- Scene C was ported next (see below); E, F, H after it, G is analysed but not ported.

## Scenes C, E, F, H port (session 5) and G (session 6): all bit-exact
- Scene table (entry flip = harness flip at the scene's first call, first displayed flip = entry+1 because the display lags one flip): A 0x28264 flip 0 (955 fr), B 0x26278 955 (957), C 0x22af4 1912 (717), D 0x1ddb4 2629 (717), E 0x24168 3346 (478), F 0x21e40 3824 (478), G 0x2747c 4302 (704), H 0x29634 5006 (250); the demo exits at flip 5257 (`stopped 0x53b35`), so the golden RAW frames end at f05256 and H has 250 verified frames (JS renders a 251st with no golden). Resume pcs after the present call: C 0x235a1, E 0x24648, F 0x2264f, H 0x298d0.
- Instructions added to the recompiler for C: div (double path, BigInt when edx >= 0x200000), cdq, one-operand imul (`R.imulhi`), rep/repnz movs (`R.n_copy`), repnz scas, sete/set<cc>, int 0x21 (AH 2c clock from a per-call counter, 2a date), push/pop/mov of segment registers (values 0x860, writes are no-ops), rcl/rcr by 1, clc/cmc/cld, fwait, xchg, lods, fstsw (mem and ax), ftst, fldpi, fptan, fprem, fld TBYTE (`R.rdf80`), parity condition codes (a `pf` variable set by sahf). Functions over 500 instructions are chunked (see above).
- 0x536f1 is the real sprintf (C prints its digit column "%13d" with it; the "FPS: %3d" overlay also goes through it): `R.n_sprintf`. Port 0x60 reads give 0 (an 0x2a would draw an FPS overlay that the golden frames do not have). 0x3d220 (XM position) must set the whole eax, not ax.
- Trace-tool fixes needed for pruned inits: natives that read memory themselves (`n_copy`, `n_fill`, `n_sprintf`) must mark their read pages, and `rd` must mark every page of a range (it only marked the first and last). Without this C, E and F diverged at frame 0/1 with a pruned init and not with the full one.
- Harness additions: `DUMPK=k,file.npz` (full RAM at flip k, before the tick increment), and the x87 stack (`fp`, st(0..7) as doubles) in the DUMPENT npz (diagnostic: at F's entry all eight registers are zero, which ruled out stale x87 contents).
- F's bug was an x87 underflow, not state: `0x3d56c..0x3d572` is four `faddp st(0),st` that pop four values from a stack that is already empty (hardware: masked invalid-operation, top wraps, nothing observable). The linear JS stack went to sp+4 every frame and was off the 16-slot array after ~120 pops, giving NaN matrices and a dim picture from frame 1. Fix in the recompiler: popping an empty stack keeps it empty (`S.sp+=S.sp<8`, applied to every fpu pop). All gens were regenerated and re-diffed.
- Sizes (pruned inits): C 2.6 MB (658 pages: the satellite photo), E 1.2 MB, F 0.9 MB, H 0.9 MB.
- Results: C 717, E 478, F 478, H 250 frames bit-exact against the harness RAW frames (`node tools/test-scene.mjs c|e|f|h INIT RAW_DIR n`); seek checkpoints verified (`tools/test-seek.mjs c|e|f|h`); `tools/uitest.mjs` shows the canvas for A, B, C, D, E, F, H and hides it in G.
- Headless Chrome speed (`node tools/bench-browser.mjs [ids]`, budget 42.9 ms/frame): A avg 18.8 ms (max 77), B avg 19.1 (max 88), C avg 11.8 (first frame up to 662 ms, JIT), D avg 9.6, E avg 24 (p95 63, 24 frames over budget), H avg 29.6 (p95 43, 14 frames over budget). Node alone: A/B ~27-29 ms.


- Scene G (0x2747c, flips 4302..5006, 704 frames) is ported (session 6), 704 frames bit-exact. How: (1) `INDCALL=1` in `re/harness.py` logs the targets of the 12 indirect call sites and the callers of the present function. G's loop (0x2747c -> 0x41dd0 -> `call [0xec106c]` = 0x4ce08) presents from 0x4ce08 at 0x4ce7d (`eax` = the picture, here 0xf65220, not the 0xebea78 pointer the other scenes use). (2) The recompiler now emits indirect calls (`call [mem]`, `call reg`) as `(FT[target]||R.bad(target))()`, `FT` being a table of every generated function; targets that the static call graph cannot see are given as extra entries (`x86js.py OUT code.bin -- 2747c 498b4 4cf6c 4ce08 4c684 4b080 4a1f0`; found by running and reading the `R.bad` error). (3) Present is nested three calls deep, so `Scene` gained a `chain`: resume = finish each open function from its call site, innermost first (`f_4ce08` at 0x4ce82, `f_41dd0` at 0x41ddd, `f_2747c` at 0x274ce). (4) New instructions: shl/shr/sar by cl, rep stos BYTE, single movs DWORD. The DPMI `int 0x31`, `lsl`, `int3`, `les`, `data16 mov seg` and `ror dx,1` sites are still emitted as throwing stubs: none is executed during the 704 frames (the run would stop with "unsupported"). The scene end (0x42200, its function-pointer table entry 0x4990c) is not generated either, only the 704 frames are verified. G's pruned init is 1.3 MB (full 8.6 MB gives the same frames).
- Speed work (hand-ported inner loops, the INLINE mechanism of `re/x86js.py`, checked by the frame diffs): the palette conversion loop that A already had, now also at 0x26eb3 (B), 0x29225 and 0x29866 (H), and the textured scanline loop 0x3d7c1 (E, F, G, H share the engine). F's two per-pixel passes (0x2256d clamp-to-byte, 0x225bf palette lookup, 192k and 96k iterations per frame) were ~55% of F. Node ms/frame: E 28.2 -> 18.9 avg, H 37.8 -> 29.2. Headless Chrome after all of this (budget 42.9, first 300 frames, avg / frames over budget): A 20.2/4, B 10.9/0, C 11.9/3, D 9.4/1, E 17.1/19, F 11.0/3, G 22.6/6, H 16.0/2 (of 251). What is left in E is per-scanline setup code (about 1.2M recompiled instructions per frame, no single hot loop), in H the `switch(pc)` dispatch of its loops; not ported further.
- The mp4 is gone from the player and from `web/assets` (a copy was kept in the session scratch dir only). The player shows nothing but the canvas; Play is offered once scene A has loaded.
